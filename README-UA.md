# Аналіз часових рядів повітряних тривог в Україні

Невеликий відтворюваний проєкт: розвідувальний аналіз часових рядів і чесний бектест прогнозування
на **найсвіжіших публічно доступних** даних про тривоги.

## Що всередині

| Команда                                     | Призначення                                                                           |
| :------------------------------------------ | :------------------------------------------------------------------------------------ |
| `python run.py`                             | Розвідувальний аналіз + бектест прогнозу добового навантаження -> `outputs/report.md` |
| `python predict.py --oblast "Kyiv City"`    | Погодинні ймовірності тривоги в одній області на найближчі 24 години (~1 хв)          |
| `python predict.py --oblast all --backtest` | Виміряна точність цієї моделі по кожній області                                       |
| `python validate.py`                        | Перехресна перевірка джерел даних між собою                                           |

**Повний посібник користувача та опис усіх виводів: [USAGE.md](USAGE.md)** (англійською).

## Швидкий старт

```bash
pip install -r requirements.txt
python run.py                 # завантажує дані (з кешем), запускає аналіз і бектест, пише outputs/report.md
python run.py --update        # те саме, але спершу повторно завантажує набір даних
python run.py --folds 1 --skip-sarima   # швидкий варіант (~40 с; повний запуск ~2 хв)
pytest -q                     # тести, зокрема перевірки відсутності витоку даних для обох бектестів
```

Усе потрапляє в `outputs/`: `report.md` (генерується автоматично, відкривайте його першим), `figures/`,
`metrics_latest_window.csv`, `predictions_latest_window.csv`, `daily_series.csv`.
Набір даних кешується в `data/` і автоматично завантажується повторно, якщо старший за 12 годин
(`--update` примусово оновлює його). Якщо GitHub недоступний, завантажувач пробує дзеркало CDN, а потім застарілий кеш;
про резервні варіанти та власне дзеркало див. USAGE.md, розділ 3.

## Дані

[Vadimkin/ukrainian-air-raid-sirens-dataset](https://github.com/Vadimkin/ukrainian-air-raid-sirens-dataset)
(MIT), **волонтерський файл** (тривоги з каналу eTryvoga). Він використовується за замовчуванням замість «офіційного»
файлу, бо оновлюється щодня і має однакову деталізацію (область) за всю історію.
Офіційний файл відстає на тижні та перейшов від рівня областей до рівня районів/громад,
що створило б штучний структурний злам.

Також доступні `--source official` та `--source combined` (офіційний файл до його кінця, далі волонтерський — експериментально).
Рівні в цих двох джерелах суттєво різняться, тому в точці зшивання виникає стрибок рівня; докладніше в USAGE.md.

Очищення: Луганську область виключено (постійна сирена, якої немає в даних), невід'ємні тривалості
відкинуто, перетинні інтервали в межах області об'єднано, ~5% тривог зі вгаданим кінцем у 30 хв залишено
й повідомлено про це. Межі днів визначаються за київським часом (Europe/Kyiv). Поточна незавершена доба виключається.

**Цільова змінна:** `alert_hours` = область-години під тривогою за добу (сума за 24 областями). Кількість
тривог *не* використовується як ціль, бо вона спотворюється змінами в порядку оголошення тривог
(кількість стартів на добу зросла ~на 65% у 2026 році, тоді як тривалість у годинах — ~на 11%).

## Метод

* Розвідувальний аналіз: ковзні середні, STL-декомпозиція, АКФ, ADF/KPSS, теплова карта «година × день тижня», розподіл за областями.
* Моделі: Naive, SeasonalNaive7, MovingAvg7/28, SeasonalMean4w, RegimeSeasonalMean (середнє за днем тижня в поточному режимі); згладжена ETS, Холта–Вінтерса(7);
  ARIMA(1,0,1), SARIMA(1,0,1)(1,0,1,7); прямий багатогоризонтний градієнтний бустинг на лагових ознаках.
* Оцінювання: бектест із ковзним початком за останні 56 повних діб, горизонти 1–7 днів;
  кожна модель бачить лише дані до свого початку (`tests/test_no_leakage.py` доводить це,
  псуючи майбутні значення). MAE / RMSE / зміщення / MASE, парні блокові бутстреп-ДІ відносно найкращої
  базової моделі та така сама оцінка на двох попередніх вікнах як перевірка стійкості.
* Також у звіті: точки зламу (режими), емпіричні 50%/80% інтервали передбачення з виміряним покриттям, а з
  `run.py --by-oblast` — моделі по областях і прогноз «знизу догори» для всієї країни.
* Жодних зовнішніх чи непублічних вхідних даних (ні даних про атаки, ні погоди, ні «інсайдерських» сигналів).

## Структура

```
run.py / predict.py / validate.py   точки входу командного рядка
src/ua_alerts/sources.py   дзеркала, перевірка кешу, перевірки якості, 
src/ua_alerts/data.py      очищення, об'єднання, погодинна/добова агрегація (волонтерське, офіційне чи комбіноване джерело)
src/ua_alerts/forecast.py  24-годинний імовірнісний прогноз (модель для однієї області) + таблиці бектесту
src/ua_alerts/pooled.py    основна 24-годинна модель: один класифікатор для всіх областей, ознаки сусідів, калібрування
src/ua_alerts/tables.py    рендерер вирівняних таблиць для всіх звітів
src/ua_alerts/eda.py       графіки та статистичні тести
src/ua_alerts/models.py    прогнозні моделі (єдиний інтерфейс fit/predict)
src/ua_alerts/evaluate.py  бектест, метрики, бутстреп, графіки
src/ua_alerts/report.py    генератор звіту в Markdown
tests/                     тести даних, резервних джерел, прогнозу, витоку даних і документації
tools/format_md_tables.py  вирівнює таблиці Markdown у документації (режим `--check` використовують тести)
```

## Обмеження

Неофіційне джерело; одне коротке тестове вікно; зміни рівня можуть відображати практику оголошення тривог,
а не рівень загрози. Проєкт аналізує сукупне навантаження тривог і не може передбачити конкретні атаки.
Не використовуйте його для рішень щодо особистої безпеки; користуйтеся офіційними каналами сповіщення.

24-годинний прогноз (об'єднана модель) лише на кілька відсотків кращий за «ту саму годину за останні чотири тижні» за оцінкою Брієра
(в середньому +2…+5% на чотирьох останніх 28-денних вікнах проти +1…+3% у попередньої моделі для однієї області)
і не кращий для кількох областей (див. бектест по всіх областях). Джерела даних також сильно розходяться з кінця 2025 року (`validate.py`).

Реалізовано з початкового списку ідей: виявлення режимів (точок зламу) і режимно-залежна модель, емпіричні
інтервали передбачення для добових прогнозів, добові моделі по областях зі сукупним прогнозом «знизу догори»
(`run.py --by-oblast`) та прогнозування на погодинній роздільності (`predict.py`). Для 24-годинної моделі також реалізовано: об'єднання
всіх областей в одну модель з ознаками сусідів, зважування навчальних даних за давністю, ваги змішування з кліматологією
по областях за ковзними вікнами валідації та калібрування. Ще не зроблено: ознаки початку/поширення тривог, квантильні прогнози погодинної моделі, вирівнювання рівня
в місці зшивання офіційного та волонтерського файлів і використання інформації про режими в погодинній задачі.
